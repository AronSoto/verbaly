# v0.4.0 — The DOM interpreter catches up with the frameworks

Date: 2026-07-04 · Status: **ready to publish** (pending release; versions aligned at 0.4.0)

## Summary

Dogfooding-driven release: everything here comes from integrating `verbaly` into its own docs site (`verbaly-web`, Astro static, DOM-interpreter path). Rich text lands in `bindDom` (React/Vue had `<Trans>`; plain HTML had nothing), plus the locale bootstrap boilerplate every consumer was going to copy-paste. No breaking changes.

## Per package

### verbaly (core) — +21 tests (78 total)

- **Added: rich text in the DOM interpreter.** Elements marked `data-verbaly-rich` render tagged messages (`'The build <em>gate</em>'`) as real elements via the shared `parseTags` tokenizer. Safety model: **whitelist of phrasing tags** (em, strong, code, b, i, u, s, small, mark, sub, sup, span, kbd, abbr, br, wbr), elements are built programmatically (`createElement` + text nodes — never `innerHTML`), **no attributes ever come from the message**, and non-whitelisted tags are unwrapped to inert text (`<script>alert(1)</script>` → the text `alert(1)`, no element). Whitelist overridable via `bindDom(v, { richTags: [...] })`. Opt-in per element — 0.3 behavior untouched without the attribute.
  - Why: without it, any sentence with inline markup forces "slot keys" (`title_start`/`title_highlight`/`title_end`) — 3 fragmented keys per sentence, translations without context, word order locked by markup. This was the #1 friction found dogfooding.
- **Added: `resolveLocale(options)` + `persistLocale(locale, storageKey?)`.** The bootstrap every app repeats: storage → `navigator.languages` (with BCP-47 narrowing `es-PE`→`es`) → fallback; persist writes storage and syncs `<html lang>`. SSR-safe (guards + try/catch for blocked storage), tree-shakeable, default key `verbaly-locale`, `storageKey: false` disables storage.
- **Added: `locales` getter** on the instance — the loaded locales (`Object.keys(dict)`, reflects `addMessages`). Feeds language switchers from one source of truth.

### @verbaly/compiler · @verbaly/vite · @verbaly/react · @verbaly/vue

- No changes. Version-aligned release only.

## Breaking changes

- None. Rich rendering is opt-in by attribute; without `data-verbaly-rich`, tags in messages stay literal text exactly as in 0.3.

## New API / signatures

- `bindDom(instance, { richTags?: string[] })` — new option.
- `data-verbaly-rich` attribute (observed; toggling re-renders).
- `resolveLocale({ supported, fallback?, storageKey? }): string` + `type ResolveLocaleOptions`.
- `persistLocale(locale, storageKey?): void`.
- `Verbaly.locales: string[]` (readonly getter).

## Docs impact (for verbaly-web)

- **`docs/dom` page:** add a "Rich text" section (`data-verbaly-rich`, whitelist + XSS model, `richTags` option) and a "Locale bootstrap" section (`resolveLocale`/`persistLocale`).
- **`docs/api` page:** add `locales` to the instance surface; add the two helpers.
- **`/changelog`:** add the 0.4.0 entry.
- **The site itself should migrate** (it's the dogfood): collapse slot keys (`title_start/_highlight/_end`, `body_before_code/_after_code`) into single rich messages, replace the hand-written detection in `scripts/i18n.ts` with `resolveLocale`/`persistLocale`, and feed `VLocale` from `i18n.locales`.
- Core README: "Plain HTML" section gains the rich-text example (already updated in this repo).

## Notes

- `<a>` is intentionally not whitelisted (useless without `href`, and attributes from messages are banned by design). If links-in-messages become a real need, design a safe mapping first (e.g. named hrefs supplied by the caller, like `<Trans>` components).
- FOUC on static sites (source-locale HTML flashes before the runtime re-renders) stays open — compiler/SSR territory, candidate for 0.5+.
