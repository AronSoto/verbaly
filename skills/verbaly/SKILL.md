# Verbaly for coding agents

Verbaly inverts the i18n flow: you write natural text in the source and the compiler extracts it, generates stable keys, per-locale catalogs and types. Never invent or hand-write catalog keys.

## The cycle

1. **Write text in the source**, wrapped in a tagged template:
   ```ts
   t`Hello ${name}, you have ${count} messages`;
   ```
   In markup it must sit in expression context: JSX ``{t`…`}``, Vue ``{{ t`…` }}`` or ``:title="t`…`"``, Svelte ``{$t`…`}``, Astro ``{t`…`}``. Display-only text is never extracted.
2. **Extract**: `npx verbaly extract` scans sources, fills `locales/<locale>.json` and refreshes the generated types. With a bundler plugin (`@verbaly/vite`, `@verbaly/unplugin`, or the framework integrations) dev-mode extraction is automatic.
3. **Check**: `npx verbaly check` exits 1 while a translation is missing or broken, or a key written in the code is in no catalog. This is the CI gate. A build with the plugin lists the same problems and goes on, broken translations first, so read its output too; `failOnMissing: true` makes the build stop instead.
4. **Translate**: `npx verbaly translate` fills gaps with the configured provider (default Claude, needs `ANTHROPIC_API_KEY`). Machine output is saved as drafts; a human accepts them with `npx verbaly review --approve`, or in the local review server (`npx verbaly-studio`, package `@verbaly/studio`). Human files round-trip via `verbaly export` / `verbaly import` (XLIFF, CSV, gettext PO). A batch the provider does not answer is retried, then reported with its keys, and everything that did answer is written: re-run to ask only for what is left.

`npx verbaly status` shows coverage per locale at any time; `npx verbaly doctor` diagnoses a broken setup. To onboard an existing JSX/TSX codebase, `npx verbaly wrap` reports hardcoded text and `--write` wraps it. Coming from another i18n library, `npx verbaly init` points the config at the catalogs you already have, and `npx verbaly migrate` ports them: it reports first, rewrites `{{name}}` to `{name}`, doubles a brace i18next showed as text, lists what it will not guess, and remembers in `.verbaly-state.json` which languages it converted, so running it again never converts them twice.

Prefer the MCP server when available: `claude mcp add verbaly -- npx -y @verbaly/mcp` exposes the cycle as tools, in the order you meet a project: `verbaly_init`, `verbaly_doctor`, `verbaly_wrap`, `verbaly_extract`, `verbaly_status`, `verbaly_missing`, `verbaly_translate`, `verbaly_write_drafts`, `verbaly_drafts`. Each answers with structured output as well as text. **When you translate yourself, save it with `verbaly_write_drafts`**: it checks each entry like a provider's against the text that ships, marks it as a draft and stamps it for that text, so never write translations into a catalog or touch `.verbaly-state.json` by hand. **Approving a draft is not one of them, and never will be**: `verbaly_drafts` shows you each machine translation next to its source so a human can decide, and accepting one is `verbaly review --approve` or `@verbaly/studio`, run by them. An agent approving its own translation is the safeguard approving itself, so the token Studio prints stays out of your prompt.

It also serves two **resources**, which is how you read the project without spending a tool call: `verbaly://config` (source locale, every locale, catalog directory, url mode) and `verbaly://catalog/{locale}` (every message of one locale, flattened the way the runtime sees it). Reading a message's text is what these are for: no tool returns it.

## Rules that keep the cycle safe

- **Keys are generated** (hash of the message). To reference one in code, keep writing the `` t`…` `` template; the build transform turns it into `t('<key>', params)`. Use `` t.id('my.key')`…` `` only when a stable human key is required. A project may instead keep its text in the catalog and call `t('my.key')`; keys that come from data compile as they are, and declaring them with `defineKeys` from `virtual:verbaly` is what lets `check` verify them and `--prune` keep them.
- **A text written in code belongs to the code.** Change a `` t`…` `` or `` t.id('k')`…` `` text in the code: an edit of it in the source catalog is replaced, with a warning. A text that lives only in the catalog is edited there, and its translations then show as outdated until someone updates them or approves them with `verbaly review --approve`.
- **Name the translation function `t`.** `const tr = useT()` runs, but `` tr`…` `` is never extracted and stays in the source language; `extract`, `doctor` and `verbaly_extract` name every such call with its file and line, in `.vue`, `.svelte` and `.astro` files too, and `--prune` keeps the translations it reads until you rename it. One `t.id` key holds one text: two texts under one key render the one written first (by file path) everywhere, and `check` names every place that disagrees.
- **Keys are typed, so a key you write has to exist.** `t`, `useT()`, `getT()` and an instance's `t` reject a key no catalog has and ask for its params. Add text through `` t`…` `` or `` t.id('k')`…` `` and run `verbaly_extract`, which writes the catalogs and the types in one go; a key that comes from data (a `string`, or a variable typed as a union of keys, whose params stay open) passes as it is, so never cast it to make it compile. **Never write a `verbaly.d.ts` by hand**: the types are generated where the framework reads them (`.verbaly/types.d.ts` in Next, `.astro/…` in Astro, `.nuxt/verbaly.d.ts` in Nuxt, `src/verbaly.d.ts` elsewhere), and `npx verbaly typegen` rewrites them for CI.
- **Text only translates inside `include`.** The default reads `src/` and `app/`, so a `` t`…` `` in `components/` of a Next app without `src/` is never extracted and shows in the source language. `verbaly_doctor` lists such files with the pattern to add; add it to `include` in `verbaly.config` instead of moving the file.
- **In a catalog written by hand, literal braces are doubled** (`{{` shows `{`). A number param is formatted for the language (`{year}` reads `2,026` in English), so pass `String(year)` for a value that is a label.
- **`""` in a catalog means untranslated** (falls back to the source language). Intentional empty text is `' '`.
- **`.verbaly-state.json` is the review state: never delete it.** It holds which translations are machine drafts and the fingerprints that flag outdated ones. If it cannot be read (a merge conflict), restore it from git: deleting it marks every draft as reviewed. `verbaly review` lists what is waiting with the source text and the translation side by side, for the human who approves it.
- **`extract --prune` waits while any source file does not parse**: such a file may read any key, so pruning then would delete live translations. Fix the file it names first (`verbaly_extract` returns them as `unparsed`), then prune.
- **Two message features are weight the compiler decides for you**: the ICU parser (544 B) and the relative-time formatter (364 B) ship only when a catalog actually uses them. Never hand-wire either. If messages reach the app after the build (a CMS, a fetched catalog) and may use them, set `icu: true` or `relative: true` in the config; otherwise such a message degrades with a warning that names what is missing.
- **Params and tags must survive translation**: `{name}` placeholders and `<em>…</em>` tags stay verbatim in every locale, or the entry is rejected.
- **Rich text is whitelisted**: messages may carry phrasing tags (`<em>`, `<strong>`, `<code>`…); links go through named tags plus a links map, never literal `<a href>` in a message.
- **`routing` says where the language lives in the URL** and is normally not written at all: a project with a `render` section is `'prefix-except-source'`, one without is `'no-prefix'`, and `'prefix-all'` exists for when no language is the default. **To switch languages, call `switchLocale` from `virtual:verbaly`**, never assemble it by hand: it is bound to the project and does the right thing in either mode (navigate, or swap in place), remembers the choice in both the cookie and storage, and sets `<html lang>`/`<html dir>`. Pass `{ navigate }` to use your framework's router. `localePath` and `localeFromPath` come from there too.
- **On a server, the URL decides the language when it carries one, and the cookie is not consulted.** Pass `routing` to the integration so it can: `verbalyHandle({ locales, routing })` in SvelteKit (plus `verbalyReroute` in `hooks.ts`, so one route tree serves every language), nothing to write in Nuxt, and `setRequestLocale(locale)` from `@verbaly/next/server` in the `[locale]` layout for Next. **Next needs that call to stay statically rendered**: without it Verbaly reads request headers, and that read makes the route dynamic. **An `app/[locale]/` tree is the one Next setup where `routing` must be written**: set `routing: 'prefix-all'` in `verbaly.config`, because the inferred `'no-prefix'` leaves `getAlternates` empty and `useSwitchLocale` swapping in place (and `setRequestLocale` warns once about exactly that). With it written, `useSwitchLocale()` navigates to the same page in the new language with no options. In Astro's own i18n routing, build the instance with `await createRequestInstance(Astro.currentLocale ?? sourceLocale)`.
- **Next with `cacheComponents` (on in `create-next-app`)**: a root layout that negotiates the language from the cookie reads the request, so it exports `export const instant = false`, or the build fails at prerender; the `[locale]` setup above stays static and needs nothing. Where there is no request at all (an OG image, a sitemap, an email), call `getT({ locale: 'es' })`, which never reads one. Rich text in a Server Component is `<Trans>` from `@verbaly/next/server`.
- **A mirrored page can carry its own messages.** With `render.inlineCatalog`, `verbaly render` writes into each page exactly the messages it renders, so that page fetches no catalog. Under a client-side router the next document brings its own, and the runtime has to be handed it: call `adoptPage({ root, path })` from `virtual:verbaly` in the hook that fires **before** the swap. Astro's `<ClientRouter />` is wired by the integration, so there you write nothing.
- **`alternateLinks` builds the hreflang set** (one entry per locale plus `x-default`) for a translated head on a server; `verbaly render` already writes it for static output. Under `no-prefix` it is empty on purpose: one URL cannot carry every hreflang.
- **Bind the head, not just the body.** A translated page with an English `<title>` and `<meta name="description">` is a half translation, and those two are most of what a search result shows: `<title data-verbaly="key">` and `<meta data-verbaly-attr='{"content":"key"}'>`. At runtime `bindDom` needs `{ root: document }` to reach them; its default root is the body.
- **`npx verbaly` comes from `@verbaly/compiler`, and it has to be a direct dev dependency.** A package manager only links a bin for a package the project depends on itself, and this one usually arrives through a framework integration, so `npx verbaly` does not resolve until you add it: `pnpm add -D @verbaly/compiler`. `npx verbaly doctor` reports it when it is missing.
- Config lives in `verbaly.config.{js,ts,json}` (`locales`, `include`, `dir`); `npx verbaly init` scaffolds it, keeps the catalogs a project already has, and detects the bundler.
- **In the browser the provider is optional.** With no `VerbalyProvider` (or Vue plugin, or `provideVerbaly`) above it, `useT()` reads the instance `virtual:verbaly` creates, so a component test needs no wrapper. On a server it is required, since every request has its own instance.
- **Coming from react-i18next**, keep the hook your components already call (a `useTranslate` wrapper can just return `useT()`), replace a key type built from the JSON (`NestedKeyOf`) with `VerbalyKey` from `virtual:verbaly`, and wait for the first catalog with `setLocale(locale).then(() => render())`: a top-level `await` there splits the bundle into many chunks. While i18next still serves some screens, give it `interpolation: { prefix: '{', suffix: '}' }` so both read the converted catalogs.
- **Terms that must not be translated go in `translate.glossary`**, never fixed by hand after the fact: `{ Verbaly: 'Verbaly', checkout: { es: 'pago' } }`. Tone and address form go in `translate.instructions`.

## Framework wiring (one-liners)

| Stack      | Setup                                                       |
| ---------- | ----------------------------------------------------------- |
| Vite SPA   | `verbaly()` from `@verbaly/vite` in `vite.config`           |
| React      | `@verbaly/react`: `VerbalyProvider` + `useT()` + `<Trans>`  |
| Vue        | `@verbaly/vue`: `verbalyPlugin` + `useT()` + `<Trans>`      |
| Svelte 5   | `@verbaly/svelte`: context + `$t` store + `<Trans>`         |
| SvelteKit  | `verbalyHandle` from `@verbaly/sveltekit` in `hooks.server` |
| Nuxt       | `modules: ['@verbaly/nuxt']`                                |
| Next.js    | `withVerbaly` from `@verbaly/next` + `/server` + `/client`  |
| Astro      | `verbaly()` from `@verbaly/astro` in `astro.config`         |
| Plain HTML | `bindDom` + `data-verbaly` attributes                       |

Full docs: https://verbaly-web.vercel.app/docs
